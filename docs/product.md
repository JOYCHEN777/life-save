# 随手存档 · Life Save — 产品需求与实现交接

整理日期：2026-10-23。本文是本项目的需求主文档，由本对话的用户决策及既有产品文档整理而成。

## 1. 协作方式与状态含义

- **需求对话（当前对话）**：讨论场景、功能、优先级、效果图和验收标准；维护本文。
- **实现对话（另一个对话）**：依据用户指定的需求编号与批次修改代码、验证效果、说明限制，并回填交付状态。
- 两个对话通过同一份文档衔接；打开同一个本地项目即可读取本文，不应假设另一个对话自动拥有全部聊天历史。
- 新想法先记录为建议。用户对某个方向的认可，不自动等于所有具体交互、技术方案或整份待办均已授权实施。
- 实现中发现需要改变产品含义的问题，列出具体决策点；普通实现细节可自主处理，不能把尚未定稿的产品选择当成用户已确认。
- 实现对话回填交付记录时保留需求编号、确认状态和优先级。两个对话更新本文前均读取最新版本，只改相关部分，避免覆盖对方更新。

本文分别标记两种状态：

| 维度 | 含义 |
| --- | --- |
| 需求状态 | 已确认、已提出待定稿、方向确认、助手建议、远期探索 |
| 交付状态 | 现有原型已有、部分已有、概念图阶段、未实现 |

“现有原型已有”指本地工作区内的既有交付，不等于已推送 GitHub 或正式上线；历史基线来自既有交付说明和当前 README，各批实现的最新验证以本文对应的交付回填为准。

## 2. 产品目标与使用者

**一句话：一个让人随手记录生活小事、快速找回记忆，并从每次点击中获得清晰反馈的生活小工具。**

- **命名状态：** “随手存档 · Life Save”为当前暂用名；用户评价“还不错”并要求保留，同时探索更简约、更抓人的名称，正式品牌未定。用户提出的“凤梨罐头”“妙妙屋／自己的奇妙小世界”“P world”“金鱼记忆”及助手扩展建议已分开记录在[命名灵感池](naming-ideas.md)，可用于当前或未来其他 App。
- 核心目标：帮用户记住做过什么、上次是什么时候、下一次期望时间还有多久；确认已经做过的事，让回看更安心。
- 首要体验：每次点一下都很爽。按下、保存、状态变化和短促反馈连贯；快速操作到这里就可以结束。
- 次级目标：通过回看了解自己，降低开始做事的门槛；后续发现合拍的人和活动。
- 典型使用状态：健忘、注意力容易分散、想随手做点什么、无聊时愿意打开看看。产品不依赖医学诊断或 MBTI 类型才能使用。
- 用户有后端开发基础；长期希望多平台支持，当前允许从简单的 Web 原型开始。正式客户端与后端技术栈未确定。
- **公开分发目标已确认（2026-10-23）：** 未来开放给其他人使用，用户安装后即可开始使用。正式产品自行管理必要的运行环境和存储，不要求使用者运行命令、手动启动服务、配置数据库或自行部署后端。本地核心功能不依赖云端服务或远程登录；首发平台、客户端框架及在线功能的账号方案仍待定。

| 场景 | 用户需要的结果 |
| --- | --- |
| 记不清上次吃过敏药的时间 | 一键记录，快速查看上次记录及已经过去多久 |
| 想给某件事设一个期望间隔 | 看到距离下一次期望时间还有多久，以及时间进度 |
| 担心门没锁、直板夹没断电 | 查看本次出门的确认时间，与上次出门明确区分 |
| 记不清猫咪早饭、晚饭、益生菌是否处理 | 按事项查看本轮确认情况和时间 |
| 完成后想多说两句 | 可选补写备注，不打断一键完成 |
| 想随手写一段话或回看生活 | 自己的生活动态集中呈现记录、备注和随手记 |
| 无聊、想回看自己或开始一点小事 | 趣味入口提供有内容的回看和足够小的开始动作 |

## 3. 已确认的核心需求

### LS-01 功能导航与首页

- **需求：已确认；交付：现有原型已有。**
- 左侧菜单可以展开并选择功能；首页让常用操作直接可点。
- 当前菜单：首页、场景清单、全部卡片、记录日历、生活动态、设置。
- 用户新增提出在“设置”下方放置“设计思路”入口，展示个人创作背景与设计理由，见 LS-19；当前尚未实现。
- 当前桌面端可收起菜单，移动端使用抽屉。后续新增功能的入口位置仍需设计。
- 验收：导航可以到达各功能；手机端可开关菜单，常用记录不必每次先打开菜单。

### LS-02 自定义生活卡片与重复记录

- **需求：已确认；交付：现有原型已有。**
- 卡片可设置名称、图标、记录或确认用途，并按需设置提醒与所属场景。
- 普通记录卡每次主动操作新增一条真实时间记录，展示上次记录及已过去时长；操作后仍能再次记录。
- 误触可撤销。当前实现只撤销该卡片最近一次记录，短暂防连点约 0.9 秒。
- 验收：正常记录两次形成两条事件；误触撤销不影响其他卡片；刷新后记录仍存在；保存失败时不能显示已保存。
- 当前限制：已有卡片不能切换用途；不支持卡片删除、排序、自定义新场景、补记过去的操作或修改历史操作时间。

### LS-03 间隔提醒与时间进度条

- **自定义间隔与进度条：已确认；交付：现有原型已有。**
- 显示“距离下一次期望时间还有多久”，配合进度条、目标时间及到期状态。
- 当前原型支持从最近一次记录起算的间隔，以及每日固定时间。固定时间是首版采用的实现选项。
- 间隔进度从 0% 到 100%，超过期望时间显示到期或超时，不代表事情已经完成。
- 验收：记录后按规则更新下一次时间；无记录时不虚构起点；每日固定时间不因晚做而向后漂移。
- 当前仅页面内提醒；页面每 30 秒及回到前台时更新。系统推送、后台提醒、暂停与本次跳过尚未定稿或实现。
- 示例规则可以修改；过敏药默认不设提醒，产品不制定用药计划。

### LS-04 一键确认与场景清单

- **需求：已确认；交付：现有原型已有。**
- 用户主动确认后留下可查看的凭据，例如“今天 08:42，你确认过门已锁”。
- 场景清单包含多张卡片，各项分别确认，展示本次清单结果。
- 当前“出门前”按手动开启的轮次确认；“猫咪照顾”和独立确认按本机日期每日确认。轮次规则是现有原型基线，后续可单独调整。
- 验收：同一轮不重复确认；新一轮保留旧历史；昨天或上次出门的确认不会显示成本轮已完成。
- 提醒到期与确认轮次独立：提醒到期不会自动清除确认；跨午夜会刷新按天轮次，手动出门轮次保留并显示开始日期。
- 确认描述用户当时的操作，不代表系统检测到了门、设备或宠物的实时状态。

### LS-05 总览次数热力图与分类彩色小方块

- **需求：已确认；交付：现有原型已有。**
- 总览用方案 A：汇总所有卡片的每日记录次数，记录越多，绿色越深。
- 单个类别用方案 B2：不同事项用不同颜色的小方块展示，采用轻微圆角，不使用条形标记或小圆点。
- 当前规则：同一事项当天有记录就显示一个固定位置的小方块；重复次数在日期详情查看。超过四项时显示前三项，其余有记录的事项以 +N 汇总。
- 当前总览及单卡详情采用固定次数档位：0、1、2–3、4–6、7+。分类包括出门前、猫咪照顾、随手记录、独立确认，按卡片当前归属划分。
- 验收：新增与撤销同步更新计数和颜色；点击日期可看具体记录、时间及备注；今天可识别，未来日期不可新增虚构记录。
- 当前默认展示近 12 周并支持翻页。新的五档时间范围见 LS-08，不能把它写成已经实现。
- 2026-10-23 新增换肤需求见 LS-16：绿色是当前原型配色；总览是否随皮肤使用其他有序色阶、分类颜色如何适配，作为皮肤设计的一部分继续定稿，不改变次数和事项的含义。

### LS-06 完成后可选「补一句」

- **需求：已确认；交付：现有原型已有。**
- 点一下确认，立刻反馈，操作就结束；完成后可选择「补一句」，也可忽略或以后补。
- 备注绑定某一次具体记录，补写或编辑不增加完成次数，不改变提醒或确认轮次。
- 当前可从完成反馈、卡片最近记录、日历日期详情或生活动态进入编辑。
- 验收：忽略备注也算完成；后来补写仍关联原记录；原事件时间不变，文字补充时间单独记录；刷新后内容存在。
- 当前支持最多 1000 字、多行、修改与清空。撤销事件时，其备注随该事件移除。

### LS-07 私人的生活动态与独立随手记

- **需求：已确认；交付：现有原型已有。**
- 集中呈现卡片记录及备注，也可以独立写一条随手记。
- 当前动态属于个人回看；“发布”不表示已公开给其他人。好友分享见 LS-14。
- 独立随手记不增加卡片记录次数，不改变提醒或确认状态。
- 验收：事件、备注、随手记能正确区分；按原始时间回看；删除随手记不影响卡片事件、备注或完成次数。
- 当前筛选为全部动态、有备注的记录、独立随手记；每次展示 40 条，可继续加载。随手记最多 1000 字，保存后可删除，不提供修改入口。
- 删除前需要确认；删除 action 携带 `updatedAt`，旧页面不能静默删除另一页面后来更新的内容。备注编辑中的草稿不会被定时刷新重建。

### LS-09 随机翻到以前的自己

- 价值：让已有生活记录值得再次打开，也让今天写下的内容以后有机会重新遇见。
- 首版入口：首页的「翻翻以前」区块；有候选内容时点「翻一张」进入回看。
- 首版素材：今天之前的真实随手记，以及今天之前、已经补过备注的历史记录；没有备注的历史操作不参与，今天的内容也不在同一天内翻出。
- 首版交互：显示原日期、来源和原文，提供「再翻一张」和「进入原记录」；同一轮优先不重复，候选耗尽后才重新开始。
- 首版空状态：没有旧内容时明确提示，并引导先留下今天，不编造回忆。
- 可选扩展：「回一句给那天的自己」，以今天的新内容回复，关联旧记录，保留原文与原时间。
- 本批暂不实现：回一句给那天的自己、好友分享和新的回忆类型；“以前”当前按本机日期判断为今天之前，不含更细的时间范围设置。
- 已验证验收：不虚构回忆；无旧内容时有合理状态；回看和翻页不增加完成次数；原始记录可进入详情或生活动态定位；原文不被修改。

### LS-10 帮我开个头

- 价值：把“想做但起不了头”变成一个可以马上尝试的小动作。
- 候选最小版本：选一件事，展示一个很小的第一步，例如“想学习”→“打开资料，只看一个标题”。
- 操作候选：「这步好了」「换个开头」，完成后可以结束，也可以再来一步。
- 待定：预设事项还是自由输入；与现有卡片是否关联；预设步骤还是接入 AI；完成第一步是否进入动态；是否支持连续拆步。
- 建议验收：第一步完成与整个目标完成明确分开；可以退出或换一个；不会自动新增用药、喂食等事实记录。

### LS-11 随便来一下

- 价值：连选功能都不想选时，给一个低门槛入口。
- 候选方案：从已具备的回忆、开头建议、印章等内容里抽取一种，先展示，由用户决定是否参与。
- 待定：参与的内容类型、是否允许偏好设置、与前两项独立入口的关系。
- 建议验收：点按钮本身不替用户确认事情、不自动写入事实记录；可跳过、可退出。

### LS-12 今天盖个什么章

- 价值：用简短、有趣的方式表达今天的状态。
- 候选方案：自选“低电量营业”“居然搞定了”“今天适合发呆”等印章，盖下时有压印反馈，可配一句话进入生活动态。
- 待定：一天能盖几次、是否允许修改、印章如何获得、是否自定义、是否进入回忆素材。
- 建议验收：印章不计入卡片完成次数；无必须连续签到的要求；跳过不会损失已有内容。

### LS-13 卡片的小性格

- 价值：通过语气、表情、图标动作让常用卡片有辨识度。
- 候选方案：猫咪卡出现爪印，学习卡轻轻翻一页；个性反馈保持短促。
- 待定：系统预设还是用户自选、与图标/主题的关系、动效强度。
- 建议验收：性格不遮挡时间与状态、不改变操作含义；兼容声音关闭和减少动态效果；确认类事项的反馈清晰安定。

## 6. 好友、个性化与远期方向

### LS-14 添加好友与互动

- **需求：后续方向已确认；具体互动待定；交付：未实现。**
- 用户希望未来可以加好友并互动。
- 助手建议从“选择一条内容分享 → 好友回应”开始，再考虑共同开始一件小事。
- 候选互动：分享某条随手记、回忆或印章；送出抱抱、击掌或文字回复；邀请朋友各完成一个小动作。
- 建议默认私人保存，由用户主动选择分享内容；不自动分享完整日历、用药记录或出门状态。
- 待定：如何加好友、分享范围、评论/回应类型、撤回与删除、屏蔽关系、是否需要消息通知。
- 多人共同照顾宠物与共享确认状态是另一个未确认场景，需要额外设计“谁做过”及重复喂食处理，不属于已定稿的好友功能。
- 不在当前原型中假装已有账号、同步或社交后端。

### LS-16 皮肤设置：预设模板与自定义图片

### LS-17 本地 SQLite 存储、本机统一存档与恢复

- **需求：本机独立存储、同一台电脑不同浏览器自动共用存档已确认；用户认可采用内嵌 SQLite（2026-10-23）；LS-17-A 第一阶段已在实现对话完成，LS-17-B 安装版仍未实施。**
- 用户明确选择“先让这台电脑上的不同浏览器自动共用存档”。近期目标不是靠手动导出／导入维持日常跨浏览器使用；账号与跨设备同步不属于本次近期实现范围，后续可选云同步的收费方向见下文。
- 用户进一步确认未来要公开分发，并要求“别人一安装，就可以用”。本机共享是近期目标，公开产品的安装即用是长期交付要求；不能把原型的开发启动方式变成普通用户的操作步骤。
- 本地核心记录与回看使用用户设备上的存储空间，不依赖开发者的远程业务服务器；用户无需单独安装 SQLite、配置数据库或为本地使用开通云服务。数据库引擎随应用交付，数据库文件在首次使用时创建。
- LS-17-A 的实际实现、验证结果、启动方式、数据位置、迁移方法和限制见下方“本批实现回填”；安装版仍需另定首发平台和客户端框架。

**LS-17-A 本批实现回填（2026-10-23）：**

- **实际完成：** 新增本机 Node HTTP 服务和 SQLite 正式存档；页面通过 `/api/bootstrap`、`/api/actions`、迁移 preview/apply 接入同一存档。保存内容覆盖卡片、场景、事件、备注、随手记、确认轮次、提醒规则、主题、壁纸和操作偏好。SQLite 事务成功并返回快照后页面才显示成功；请求 ID 幂等、事件 ID 去重、备注版本冲突、撤销、并发 action、正式／测试空间隔离均已实现。壁纸文件保存到存档目录的 `files/`，SQLite 保存相对引用。
- **启动方式：** `node prototype/server.mjs`，默认服务地址 `http://127.0.0.1:8787/prototype/`。仍可用 Python 在 `8080` 提供页面，但本机 SQLite 服务必须同时运行；当前是开发启动命令，不是安装即用流程。
- **数据位置：** macOS 默认 `~/Library/Application Support/Life Save/data.sqlite`，壁纸在同一存档目录的 `files/`；测试空间写入该目录下 `tests/test-<hash>/data.sqlite`。可用 `LIFE_SAVE_DATA_DIR` 指定开发验证目录。路径不依赖项目目录、Git 分支、预览端口或 query；query 中的 `check` 只映射明确的测试空间。
- **迁移方法：** 在持有旧 `localStorage` 的浏览器打开设置页，选择“迁入浏览器旧存档”，先查看来源摘要和合并预览，再选择“合并迁入”“以来源为准”或“保留当前”。原浏览器来源不删除；服务端迁入前保存当前正式存档备份，事务失败回滚，按来源内容哈希避免同一来源重复计数。浏览器不能直接读取另一个浏览器的 `localStorage`。
- **验证结果：** `cd prototype && npm test` 通过，37/37 项测试通过；覆盖 SQLite 重启持久化、两个并发记录不互相覆盖、request ID 重试不重复、备注过时版本冲突、测试空间隔离、迁移 preview/apply 与重复迁入、迁移合并保留已有卡片／偏好／外观、壁纸文件引用和客户端错误包装。浏览器通过本机服务两个独立预览页验证一页新增后另一页约 5 秒内看到；设置页实际发现并预览了旧来源（其中一份为 8 张卡片、4 条记录、1 条随手记），未未经选择直接迁入。正式库中的浏览器验证记录已撤销恢复为 0 条记录。
- **已知限制：** 本批未完成安装包、自动启动／退出、无 Node 环境安装、升级结构迁移、Windows/Linux 实机验证，也未在真实 Chrome 浏览器完成双向验收；当前验证使用两个独立 Codex 预览页，Chrome 控制面不可用。没有完整备份管理界面、导出／导入和磁盘故障恢复；旧 `localStorage` 来源仍需在原浏览器逐个迁入。服务关闭时页面保留已读内容但不能宣告新写入成功；未实现离线待同步队列。Node 22 的 `node:sqlite` 当前仍有实验性提示。LS-17-B 仍不能标记为完成。

**用户提供的故障排查记录（本对话未独立复核，数量仅为报告时快照）：**

- Codex 内置预览环境有 8 张卡片、4 条历史记录、1 条随手记；Chrome 当前环境有 7 张默认卡片、0 条记录。
- 两边地址看起来相同，但浏览器／Profile／预览容器的本地存储互相隔离。用户看到默认卡片、空日历或 0 条动态，误以为历史丢失。
- 用户转述的排查已确认：在当前环境新建记录可正常进入生活动态；仅修复筛选无法消除多份独立存档的问题。
- 记录与外观、设置的存储范围应逐项核对，不能仅凭 URL 相同或主题相同推断加载的是同一份记录。现有记录存储还受 pathname／query 的应用命名规则影响。

**建议的近期原型接入方案（SQLite 方向已认可，具体运行方式待实现评估）：**

- 同一本机操作系统用户运行一个本地应用服务，以固定用户数据目录中的 SQLite 作为正式存档；Codex 预览、Chrome 等通过该服务读写同一存档。
- 浏览器负责展示与交互，可以有缓存，但不能再各自把 localStorage 当成互不关联的正式存档。改用另一种浏览器本地数据库也不能单独解决跨容器共享。
- 存档具有稳定身份；数据目录不依赖临时预览目录、Git 分支、工作树、端口或任意 query。重启服务、更换代码目录不会自动创建另一份正式存档。
- “同一台电脑”还要求连接同一本地服务／存档；不同系统用户、远端执行器或各自独立启动的服务不自动共享。首次实施须实际验证 Codex 预览与 Chrome 都能访问同一服务。
- 建议近期仅监听本机回环地址；账号、互联网访问、手机跨设备使用与多人共享另行设计。SQLite 方向已认可，后端语言与客户端框架未指定；不能仅将 SQLite/WASM 放进各浏览器的私有存储，就认为达成了跨浏览器共享。

**面向公开分发的本地运行要求与方案建议：**

- 本地使用路径应在首次打开时建立个人存档并开始记录，不依赖远程账号校验。账号可作为以后跨设备同步、好友互动的入口，具体流程另定。
- 安装式客户端自行管理持久化目录、数据库及所需进程的启动与退出。SQLite 引擎与必要运行依赖随应用交付，无需用户另装数据库服务；Tauri、Electron 等客户端框架未选定。
- 安装式客户端拥有内嵌数据库，并不自动让任意浏览器读到它。若正式产品继续支持本机多浏览器访问同一存档，需要另行设计由应用管理的本机访问服务；另一种方向是使用账号连接统一云端存档。普通网站／PWA 从不同浏览器安装，也不会因此共享浏览器本地存储。
- 本地核心记录与回看不依赖互联网；正式安装版应自带运行所需的界面和资源。本机可靠保存后才显示“已保存”；若以后增加云同步，另外呈现“待同步／已同步”等状态。断开互联网与本机存储进程不可用是不同情形：后者必须提示保存失败，不产生互不关联的新存档；云同步队列留待后续设计。
- 如增加云端能力，由开发者部署与维护公共后端，每位用户拥有独立数据；好友互动只共享明确选择的内容，公开提供 App 不等于公开生活记录。本机不同操作系统用户也不应默认混用同一存档。
- 保留多平台目标，首发手机、桌面或 Web/PWA 仍待决定。客户端安装、更新与数据升级应保留已有存档；更换设备、卸载重装后的恢复能力须结合备份／账号方案另定，不能由“安装即用”推导出自动恢复承诺。

**可选云同步与收费方向：**

- **方向确认（2026-10-23）：** 用户认可将可选云同步作为后续收费功能；价格、计费方式、套餐权益和实现排期尚未确定。本次仅记录需求。

- 云同步有持续的存储与服务成本，可以考虑月付／年付；是否订阅、设备数、容量、壁纸是否同步及试用规则待定，不在当前原型接入收费流程。

1. 先保存已有来源的完整快照，列出卡片、事件、随手记、设置与外观资源的概况，再选择迁入来源。本轮不直接移动或覆盖用户数据。
2. 以已包含真实历史的预览存档作为主档候选；Chrome 的纯初始化默认卡片不能自动覆盖已有主档，也不应不加判断地再导入一套默认卡片。
3. 一个浏览器不能直接读取另一个浏览器的私有 localStorage。迁入应在持有旧存档的环境执行，或由该环境导出后导入本地服务；本地服务不能仅靠相同 URL 自动发现另一容器里的数据。
4. 若两个来源都有真实内容，先展示合并预览。同源事件按稳定 ID 去重；不同来源同名卡片、相近时间的事件不直接判定为同一条。场景、卡片、事件、备注和轮次之间的关联必须保留。
5. 重复执行同一来源的迁入不产生重复记录；发生错误不留下半份迁入数据。保留旧数据与导入前备份，直到迁入结果核对完成。

**连接、并发和测试空间建议：**

- 服务未连接、正在读取、读取失败、正式存档确实为空，是四种不同状态。不能把服务异常降级成“默认卡片 + 0 条记录”。
- 仅针对上述近期原型方案，建议以本地服务确认持久化写入作为成功条件。服务不可用时保留正在输入的内容并允许重试；离线可记及待同步队列需要单独定稿，不悄悄写到新的私人副本后宣告已共用存档。这不是已确认规则，也不要求未来安装式客户端必须联网才能保存。
- 跨浏览器操作以具体事件或变更为单位写入，不让旧页面用整个本地快照覆盖新存档；重试同一次提交不重复新增。
- 不同浏览器新增的不同事件均保留；同时编辑同一备注时提示冲突并保留草稿；旧页面不能把已撤销的事件重新写回来。外观可以考虑最后一次明确应用生效，规则待确认。
- 切回页面时重新读取当前状态；停留中的其他浏览器应在约定的时间内更新，刷新机制与延迟目标由实现批次确定。
- 正式与测试空间继续隔离是建议边界。测试身份必须对使用者可见，并贯穿服务端记录、设置、壁纸与资源；测试不能因为接入共享服务而写进正式库。
- 只有明确的测试入口／标识才切换测试空间，普通 query 不应无提示地生成新正式存档。开发诊断可展示存档名、短编号及连接状态；普通用户页面不必暴露数据库路径等实现细节。

**备份与恢复建议（独立于共享能力，尚待确认范围）：**

- 增加完整存档导出和受控导入，明确是否包含壁纸、外观和操作设置。导入前展示内容摘要与合并／替换结果，替换前保留可恢复副本。
- 迁移、导入和结构升级前生成一致性备份；定期自动备份的频率、保留数量及存储位置待定。
- 同一个浏览器里的副本不能抵御该浏览器数据被清理；同一磁盘的数据库备份不能抵御磁盘故障。用户导出的独立副本可作为额外恢复路径，不能把“共享成功”表述成“已经备份”。

**建议验收：**

- 在 Codex 预览新增卡片、事件和随手记，在 Chrome 连接同一正式存档后可见并能继续操作；反向操作也成立。
- 清理其中一个浏览器的站点数据后，重新连接服务仍能读取正式存档；重启服务不会丢记录或回到默认数据。
- 两边近乎同时新增记录不互相覆盖；重试一次提交不重复记录；同一备注的过时修改不会静默覆盖新版。
- 服务关闭或读取失败时显示准确状态，不显示假的空存档；恢复连接后可继续使用。
- 在测试空间记录、换肤及清理测试数据，正式空间的记录与外观不受影响。
- 旧数据迁入保持时间、ID 或可追溯映射及备注关联；反复迁入不增重，失败可恢复；按迁入时各来源的实际内容核对，不能把报告中的 8／4／1 固定为永久验收值。

**仍需定稿：** 首发平台与客户端框架；正式产品是否延续浏览器访问及其共享方式；应用管理本地服务的生命周期；偏好设置的共享粒度；旧来源冲突的合并交互；用户备份功能的范围、频率和恢复方式；测试入口；与其他需求的排期。本地核心功能不依赖互联网，SQLite 随应用交付已作为本轮交接方向，不再列为未决问题。

### LS-18 生活小地图与每日自动日记

- **需求：方向确认，用户要求记入需求（2026-10-23）；首版范围建议及具体交互待定稿；交付：未实现。**
- 用户原始想法：在 App 的小地图上复刻自己每天做了什么；点击家选择活动，点击马路选择开车／地铁，到公司记录上班打卡，再根据这些点选生成每天的日记。
- 核心价值：把写日记变成在自己的小世界里走一遍今天，用轻量点选留下生活轨迹；地图本身也能用于回忆。
- 本轮记录需求，开发批次与全局优先级尚未指定。

**核心操作路径：**

`选择一天 → 点击地点／路段 → 选择做过的事／出行方式 → 汇成当天时间线 → 生成可编辑的日记`

| 地图位置 | 可选活动示例 |
| --- | --- |
| 家 | 起床、做饭、吃饭、打游戏、看电影、照顾猫咪 |
| 马路／通勤路段 | 开车、地铁、步行；可选补充堵车、听播客等细节 |
| 公司 | 上班打卡、开会、专注工作、与同事吃饭、下班 |
| 其他地点（扩展候选） | 咖啡店、健身房、公园、自定义常去地点 |

活动为示例；预设内容、自定义能力与具体入口仍待设计。

**建议的第一版范围：**

- 一张包含家、路段和公司的生活小地图，点击位置即可选择活动；不要求先完成角色移动或走完固定路线才能记录。
- 点选形成当天的活动时间线，并在地图上呈现已记录的轨迹；支持一天内多次往返与重复活动。
- 用户主动点击生成入口（候选文案「收好今天」），根据当天记录生成日记草稿，可修改、保存与按日期回看。自动定时生成不是本次已定规则。
- 保留可选的「补一句」，例如“今天终于解决了那个烦人的问题”，为日记提供当天独有的细节；不填写也能完成记录。

**设计原则与已有功能的关系：**

- 常用记录尽量在选择地点、选择活动两步内完成；不强制填心情、精确时间或长表单。
- 日记以真实记录和用户补充为依据，不编造心情、对话、经历或缺失的时间；未记录不能写成没有发生。
- 地图记录、现有卡片、日历和生活动态之间应保留来源关联。同一次操作若关联已有卡片，只形成一次事实记录；生成、编辑或回看日记不增加活动次数。
- 补记与复用通勤流程值得支持，但发生时间、录入时间、缺失时间和重复记录的规则需先定稿；复用模板不能自动声称今天已经完成。
- 重新生成日记时保护用户已编辑的文字；地图浏览与日记生成失败不能影响已经保存的原始活动。

**后续体验候选：**

- 翻到某一天，小地图亮起当天去过的地方，再展开那天的故事。
- 自定义地点、地图布置与装饰、常用通勤模板、照片或语音补充、月度回顾。
- 首版建议采用示意地图；真实地图、定位与自动轨迹采集尚未提出实施要求。地图记录与 LS-15 的宠物／世界养成分别定范围。

**建议验收：**

- 完成“家中活动 → 地铁通勤 → 公司打卡 → 回家”的记录后，地图与时间线能对应展示，日记包含已记录内容。
- 同一天多次到访同一地点或重复活动不会被错误合并；关联卡片时不会重复计数。
- 不补充文字也能记录并生成日记；空白日期不虚构一天的经历，缺少细节时不自动补成事实。
- 日记可以修改、保存并在刷新后回看；重新生成不会静默覆盖手写内容。

**仍需定稿：** 地图视觉与入口、地点和活动的自定义范围、实时记录与事后补记的首版边界、时间排序规则、与卡片／动态的具体关联、日记风格及生成方式、编辑与重新生成的交互、整体排期。

### LS-20 流水账卡片与临时生活事件

- **需求：用户已提出，先分析与已有两类卡片的区别，再设计（2026-10-23）；交付：需求分析，未实现。**
- 用户原始场景：“今天买了猫粮”，不一定有固定周期，但想留下记录。暂按“生活流水记录”理解，用户尚未提出金额统计、预算或财务账本要求。
- **已知基线：** LS-02 的普通记录卡可以不设置提醒／固定周期；LS-04 的确认卡按本轮判断是否确认；LS-07 已有独立文字随手记。因此，“没有固定周期”本身不构成新卡片类型的充分理由。

**三种使用意图的比较（新类型的定位尚待定稿）：**

| 维度 | 现有记录卡 | 现有确认卡 | 拟议流水账入口 |
| --- | --- | --- | --- |
| 核心问题 | 这件事上次何时发生、记录过几次 | 我这一次／这一轮确认过了吗 | 今天发生了什么、那次具体是什么 |
| 事项内容 | 预先定义同一种事项，每次点按新增事件 | 预先定义待确认事项，本轮确认后有状态 | 每条可以不同，临时发生也可以直接写 |
| 周期 | 可不设周期，提醒是可选能力 | 依赖本轮／本日的确认边界，和提醒独立 | 默认不依赖周期，不产生“今日未完成” |
| 操作 | 一键记时间，再可选补一句 | 一键确认，本轮不重复确认 | 需要输入或选择事件内容，再保存；不能凭空知道用户做了什么 |
| 主要回看信息 | 最近一次时间、间隔、历史次数 | 本轮确认状态与确认时间 | 日期、事件内容及可选归类 |

**“买猫粮”的两种合理表达：**

- 若希望持续关注购买猫粮的时间，可以建立不设提醒的“买猫粮”记录卡；每次购买点一下，品牌、规格等用备注补充。这属于现有记录卡的使用方式。
- 若只是今天临时想记下买猫粮，明天又想记收到快递、剪了头发，则更适合一个通用或按主题组织的流水账入口，不必为每件偶发小事先建立一张长期卡片。

**与已有随手记的关系及设计候选：**

- 建议优先复用 LS-07 的随手记能力，把流水账卡片视为更容易找到的记录入口或主题容器；生活动态继续作为集中回看视图，同一条内容不因出现在两个地方而复制成两份。
- 原型已有“文字 → 保存 → 动态回看”的路径；可能的新增价值是卡片页也能快速进入、按主题归档或回看最近几条，而不是单独再建一套近似文字记录。
- 轻量路径候选：点流水账入口 → 输入一句发生的事（或选择明确的快捷事项）→ 保存并反馈。时间可默认当前；默认值是录入时间，不能把事后输入自动认定为实际发生时刻。是否支持补记日期／时间另行定稿。
- 通用流水账与“猫咪日常”等主题流水账都可探索；主题是否可选、是否允许多个容器、常用事项能否转成固定记录卡，尚未选择。
- 不新增待办状态、周期进度条或每天必须完成的压力。图片、语音、金额结构化等保留为后续讨论，不自动加入本次范围。
- 日历如何展示流水账、是否计入一种新的“生活记录数”需要单独决定；当前随手记不增加卡片次数的规则保持不变。编辑文字、增加备注、在动态与卡片重复展示不能额外增加记录次数。

**下一步待定：** 用户主要需要不建卡的随手录入，还是按主题持续积累；入口名称与位置；每条最少需要的内容；日期与补记；和现有随手记的复用方式；日历与次数口径。上述方案均是助手分析建议，尚未授权代码改造。

## 7. 贯穿所有功能的产品边界

这些约束来自现有原型规则与设计整理；新增方案应延续，若要改变，明确说明影响。

1. **一键操作独立完成。** 备注、盖章、分享或奖励不能成为完成真实记录的必填步骤。
2. **反馈以保存结果为准。** 按压反馈可即时开始，保存成功后才宣告成功；失败明确提示。
3. **真实事件、备注、随手记与趣味行为区分。** 不能因为翻回忆、回复、盖章或点击随机入口而增加用药、喂食或锁门次数。
4. **保留时间语义。** 历史操作时间不因补写文字而改变；未来若支持补记，发生时间与录入时间应区分。
5. **未记录不代表未发生。** 用药卡只能说明上次记录时间，不能推断用户没有服药或自动建议停药；不奖励更多用药、重复喂食、延长停药或反复确认。
6. **趣味体验可结束。** 可以跳过、退出、关闭音效、减少动效；不引入断签惩罚。
7. **已有数据要保留。** 升级、撤销、修改及跨标签页冲突要有清楚语义，不能用示例覆盖用户记录。
8. **视觉变化保持功能含义。** 保留已选 B2 小方块和一键操作规则；按 LS-16 扩展可选皮肤。新的范围布局、趣味入口与皮肤先定设计，不通过换肤改变记录语义或功能布局。
